# AI 屏幕助手提速调研与方案（汇总版）

调研日期：2026-11-02
调研方式：6 路并行联网调研（共 120+ 次搜索与文献抓取），本文为合并收敛稿。
覆盖范围：业界屏幕操作 Agent、LLM API 层提速、Windows 桌面确定性自动化、实时交互 AI（语音/Realtime）、实时游戏 AI、秒杀/抢票延迟工程（含合规边界）。

---

## 一、现状：一步到底慢在哪

当前一步的完整链条（全串行）：

| 环节 | 耗时量级 | 备注 |
|---|---|---|
| 模型调用（思考开） | 首字约 2.4 秒，整轮 3~8 秒 | 关思考压到极短后约 1.1 秒出首字 |
| 鼠标动作 | 约 0.3 秒 | 含平滑移动 |
| 固定等待 | 0.7~1.2 秒 | 等界面渲染，盲等 |
| 截图编码上传 | 数百毫秒 | PNG 最长边 2200px |
| 下一轮模型调用 | 同第一行 | 循环往复 |

一个 10 步任务 = 10 次完整模型往返 = 几十秒到几分钟。对照：业界公认这种"截图循环"是视觉 Agent 最慢的形态（每步 5~15 秒常态），但头部产品已有多条成熟出路。

## 二、六路调研核心结论

### 1. 业界屏幕/浏览器操作 Agent（OpenAI Operator、Claude、UFO²、browser-use、UI-TARS 等）

- **两大路线**：纯视觉（截图进模型出坐标，通用但慢贵，每步 5~15 秒）vs 结构化（DOM/无障碍树文本，每步约 3 秒、定位确定性）。趋势是混合：树为主、截图兜底。
- **动作批处理已是行业标配**：OpenAI CUA 一个响应可含多个动作；Claude 2026 GA 加入 batch actions + wait 原子动作。
- **推测执行有专门论文**：慢 Actor 推理时快 Speculator 预启动下一步，命中约 55%，端到端无损加速约 20%（arXiv 2510.04371）。
- **KV-cache 命中率是生产 Agent 第一指标**（Manus 官方）：前缀稳定、只追加不修改、易变内容放最后。
- **输出 token 时间成本约为输入的 215 倍**（browser-use 实测：1000 输入 token 仅 29.1ms，10 个输出 token 62.6ms），动作语法极简化（10~15 token/动作）。
- **截图观察一次约 1 万+ token**，每张截图另加约 0.8 秒图像编码延迟（browser-use）。
- **重复任务不走模型**：PreAct 轨迹编译成状态机、回放快约一个数量级；Agent Workflow Memory 在 WebArena 提升 24.6%；Skyvern learn-replay。
- 基准数字：browser-use 约 3 秒/步；OSWorld 典型 CUA 每步 5~15+ 秒；无障碍树点击个位数毫秒、宣称比截图路径快约百倍。

### 2. LLM API 层（重点：智谱 GLM）

- **智谱支持隐式上下文缓存**：前缀字节级一致自动命中，命中价约 2.9 折，prefill 加快；要求前缀 ≥500 token、稳定内容放最前、不加时间戳；可从 `usage.prompt_tokens_details.cached_tokens` 观察命中。业界实测缓存命中 TTFT 最高降 80%+。
- **重要待实测项（纠正此前结论）**：智谱国内站文档写明 GLM-5.3 系列**支持 `reasoning_effort` 三档：max（默认）/high/low**（此前只查到 z.ai 海外文档的"开/关"说法）。已探测 low 请求成功，但三档实际思考长度差异未实测。
- **GLM 专属 `tool_stream: true`**：配合 stream 后工具参数以增量下发，官方推荐组合，是"边流边执行"的基础。
- **图片开销**：视觉 token 随像素数近似二次增长；Anthropic 官方建议桌面任务 1024×768 / 1280×720、避免超 1920×1080（模型侧也只保留 1568 长边）。我们发 2200px PNG 明显偏大。JPEG q85 传输 <1ms；base64 有 33% 膨胀。
- **连接层**：keep-alive 复用每轮省 TLS+TCP 握手约 100~130ms（实测案例 TTFT 800ms→200ms 主要靠连接预热+复用）。
- **模型分层**：混合路由端到端延迟约降 30~70%；GLM-5.3-FlashX 生成 200 token/s、比 Flash 快约 5 倍（价格 2.5 倍），可做关键决策轮。

### 3. Windows 桌面确定性路径（UIA / 事件 / 键盘 / 宏）

- **UIA 无障碍树**：CacheRequest 式一次查询几十毫秒拿整棵子树，定位零误差；树点击"两次 COM 调用、个位数毫秒"。
- **兼容性红线**：微信 4.x 主动屏蔽 UIA（普通客户端只拿空树）；Chrome 需加 `--force-renderer-accessibility`；Electron 默认关；游戏/自绘无树。**结论：树只能做部分应用的快速通道，视觉链路必须保留兜底。**
- **微软 UFO² 混合管线**（标杆）：UIA 树 + 视觉检测按 IoU 融合，UIA 覆盖了 Windows Agent Arena 27.9% / OSWorld-W 56.7% 的可交互元素；其推测多步规划一次出 k 步、逐步校验，步数最多降 51.5%。
- **事件驱动唤起**：SetWinEventHook / UIA 事件 / 剪贴板监听空闲近零开销、变化毫秒级通知；但 UIA 事件有误报、不保证送达，必须保留低频兜底轮询。
- **键盘优先**：Anthropic 官方建议 agent 优先键盘路径（快捷键/Tab/Enter），更快且对定位误差免疫；CoAct-1（OSWorld SOTA）把可脚本化动作从 GUI 挪出去。
- **宏录制回放**：Power Automate 模式（选择器序列 + 失败降级图像匹配 + 唤起重学）；确定性回放报告每步延迟中位数降 98.3%。
- **局部/增量截图**：两帧脏区只编码变化区（桌面场景常 <10% 像素）；控件矩形小图比全窗口低 1~2 个数量级。

### 4. 实时交互 AI（Realtime API / 语音）

- 五大手法：持久连接+服务端事件推送、WebRTC 传输、语义端点检测替代固定静默超时（省 200~400ms）、VAD 打断即作废重算、增量推理（部分结果预填）。
- **延迟预算方法论（Soniox 800ms 预算表）**：顺序执行 1180ms，流水线重叠后压进 800ms；核心是"重叠而非逐段加速"，度量"首产出"而非总时长。
- **乐观执行+回滚**：GGPO 回滚网络码（预测、快照、重模拟）；语音边生成边播、打断封顶错误代价。不可逆动作必须设确认门（Operator 的 monitor 模型）。
- 常驻小模型"盯屏/端点判定"+大模型关键节点介入，是 watcher/worker 标准分层。

### 5. 实时游戏 AI（OpenAI Five、AlphaStar、绝悟、VPT、Helix）

- **没有谁每帧跑大模型**。决策频率：OpenAI Five 7.5Hz（133ms/次）、AlphaStar 约 5.6Hz（180ms/次）、绝悟 5Hz（200ms/次）；每次输出 1 个动作，决策间隔内由引擎持续执行上一指令（动作保持）。
- **端到端反应延迟**：AlphaStar 约 110ms+166ms 人性化延迟；OpenAI Five 平均 217ms；对比人类视觉反应约 250ms。
- **感知全部结构化压缩**：OpenAI Five 完全不用画面（1.6 万个结构化数值）；AlphaStar 用 128×128 特征层+实体列表；视觉路线（VPT）必须降到 128×128+帧堆叠才能实时。反面教材：sentdex GTA V 直接送屏帧，感知超时导致转向滞后。
- **快慢双层**：Figure Helix 规划 7~9Hz（110~140ms）+ 执行 200Hz（5ms）；机器人 ACT 动作块一次预测 90 步（约 1.8 秒）+时间集成平滑。
- **限速层是标配**：AlphaStar 专门加监控层限制 APM（264）并加延迟才"像人"——决策与执行之间应有速率/合法性过滤。
- **注入延迟可忽略**：SendInput 亚毫秒到几毫秒，瓶颈 100% 在决策端。

### 6. 秒杀/抢票延迟工程（含合规边界）

- **连接预热**：完整 HTTPS 新连接 3~4 个 RTT（DNS 60~120ms + TCP + TLS），preconnect/keep-alive 摊销后约 0；开抢前把连接焐热是收益最确定的手段。
- **时钟对齐**：不信本地钟，本地时间+服务器 offset；NTP 公网几十毫秒、LAN 亚毫秒。意义在于把"预热动作"和"正式动作"排到精确时间轴上。
- **请求预组装**：登录态/token/表单提前备好，人工 5~10 秒的流程脚本压到 1 秒内。
- **重试风暴**：指数退避必须加 jitter + 重试预算 + 熔断；时间敏感场景开抢瞬间 1~2 次快速重试有效，被限流后继续猛打只会被拉黑。
- **瘦 payload**：传输时间与体积成正比；压缩实测降 78% 体积、改善 110ms。
- **API vs 浏览器 UI**：API 约 20ms vs 浏览器呈现 300~500ms；浏览器自动化的最大隐性成本是冷启动（长驻复用是数量级优化）。
- **人工 vs 脚本拆解**：感知（人 220~250ms vs 截图/事件 1~50ms）、注入（<10ms）、连接（预热后约 0）、全流程（人 5~10 秒 vs 脚本 <1 秒）。
- **合规红线（必须遵守）**：平台条款普遍禁止自动化抢购；12306 明确"加速包不加票额"并曾拒出票 105.6 万张；国内已有抢票软件刑案（刑法 285/286 条，"苏超"代抢案主犯获刑三年）；美国 BOTS Act 属联邦违法。**延迟工程本身中立：用于自己的电脑、自己的账号、授权场景正当；用于第三方平台抢占稀缺资源即触线。我们的助手只做前者。**
- 量化目标（NN/g 三阈值）：0.1 秒内给"即时反馈感"，1 秒内完成主流操作，超 10 秒必须有进度反馈。

## 三、核心洞察（六路合并提炼）

1. **省一次往返 > 加快一次往返**。动作批处理、动作队列、宏回放的本质都是减少"过模型的次数"。每省一轮 = 省一次 3~8 秒。
2. **决策与执行必须解耦**。游戏 AI（5~7Hz 决策+引擎高频执行）、机器人（1~7Hz 规划+200Hz 控制）、语音（端点检测+流式合成）全是同一句话：慢的大脑出计划，快的本地环干活。我们现在是"每步都等大脑"。
3. **感知要从像素走向结构**。树/OCR/控件列表是"实体列表"，截图只是兜底。感知通道越结构化，token 越少、定位越准、重试越少。
4. **固定等待全部消灭**。盲等换成画面稳定检测（毫秒级 diff）或事件驱动；语音界"端点检测替代固定静默"同构。
5. **上下文工程就是延迟工程**。缓存命中（智谱隐式缓存）、输出极简化（215 倍时间差）、工具说明固定化，三项都是零风险纯赚。
6. **快慢分层是常态**。本地/小模型/规则挡在前面处理高频简单步，云端大模型只在规划、异常、不可逆动作介入。
7. **乐观执行要分级**。可逆动作（移动、悬停、聚焦）可以抢跑，不可逆动作（发送、删除、支付）必须设门。这正好与我们已有的 dry_run、焦点护栏、安全确认机制衔接。

## 四、方案总表

| 方案 | 内容 | 预期收益 | 风险/代价 | 工作量 |
|---|---|---|---|---|
| A 榨干现有链路 | ① 实测 reasoning_effort 三档并启用 low ② 截图降为 1280~1568 长边 + JPEG q85 ③ 固定等待改"画面稳定检测"（复用现有 diff，最多 0.3s 封顶）④ 缓存命中监控+空闲保温 ⑤ 核对轮合并进下一轮决策 | 单步 5~8 秒 → 2~4 秒 | ⑤ 需重新设计防编造配合 | ①②③④ 低，⑤ 中 |
| B 一轮多动作（动作队列） | 放开"一轮一个动作"，允许一次输出 2~4 个高置信连续动作，逐步执行逐步校验，异常即停 | 填表/搜索类任务步数减半以上 | 与现有 sense-act-verify 保守理念冲突，需好校验 | 中 |
| C 键盘优先 | 提示词+工具层面规定：快捷键 > ctrl+f 搜索 > Tab 导航 > 坐标点击 | 动作执行 <10ms，纯增益 | 焦点管理需校验 | 低 |
| D UIA 树混合感知 | 支持树的应用先树后图：控件树转文本喂模型，模型点名不估坐标；微信 4.x/Electron 自动回落视觉 | 定位零误差、观测 token 降 1~2 个数量级 | 兼容性分裂，维护两套感知 | 高（1~2 周） |
| E 宏录制回放 | 首次成功后把动作序列+校验锚点存为宏（入记忆库），重复任务回放不再调模型，失败降级唤起 AI 重学 | 重复任务毫秒级，"越用越快" | 应用改版宏失效，需降级闭环 | 高 |
| F 推测执行/流水线 | tool_stream 增量解析提前预移动鼠标；可逆动作乐观执行，不可逆设门 | 1.3~1.7 倍（论文实测） | 工程复杂，需要精确的流式解析 | 高 |
| G 本地小模型盯屏 | OmniParser/UI-TARS 级本地模型做高频眼睛，云端只做关键决策 | 决策间隔填充、本地毫秒级感知 | 需要显卡、部署维护 | 高 |
| H 双速循环（游戏 AI 式，新增） | 大模型低频出"动作块"（N 步队列），本地循环高频执行+每步校验，块耗尽或校验失败才回炉重规划；决策间隔内延续上一动作而非干等（ML-Agents 模式） | 模型调用次数降 50%+，连续操作成流 | 需要可靠的步间校验（与 D 配合最佳） | 高 |
| I 秒杀式工程细化（新增，并入 A 的深化项） | 模型请求预组装（固定部分模板化）、动作模板本地直出（确定性指令不过模型）、单调时钟给动作打 deadline、重试加 jitter、常驻复用一切句柄/连接 | 消灭冷启动与固定开销，向 NN/g"0.1 秒反馈感"靠拢 | 纯工程，风险低 | 中 |

## 五、推荐落地路线

**第一波（低风险纯赚）**：A 的 ①②③④ + C + I 的预组装部分。预期单步从 5~8 秒压到 2~4 秒，无架构改动。
**第二波（理念调整，单独出方案确认）**：A 的 ⑤（合并核对轮，需重设计防编造配合）+ B（动作队列）。
**第三波（架构级，视效果决定）**：D（UIA 混合感知，非微信应用先试点）→ E（宏回放，与记忆库天然契合）→ H（双速循环，依赖 D/B 的校验底座）。
**长期观察**：F、G。

量化目标（对齐 NN/g）：确定性动作 0.1 秒内有反馈；常规操作 1 秒内完成；任何超 10 秒的任务必须有实时进度（思考流式框已是第一步）。
